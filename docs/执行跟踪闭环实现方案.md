# 执行跟踪闭环（实际进度填报 + 三版计划生成/对比）· 实现方案

> 范围：房地产开发运营计划系统（代建三级计划管理）· P0 收尾增强
> 依据：`docs/需求规格说明书_v0.2.md` §6.1、交接提示词 §四、「标准库版本化实现方案」§11 边界项
> 目标：把"计划只生成不跟踪"补成**闭环**——① 实际进度可逐节点填报 → ② 自动对比计划与实际触发预警 → ③ 内控/考核/履约三版可一键生成并同屏对比（代建管控特色交付物）
> 适用前提：单人使用、暂不启用审批流（用户 2026-09-12 决策）

## 0. TL;DR

| 项 | 结论 |
|---|---|
| 当前缺口 | 仅生成「内控」版；`actual_finish` 有字段无录入 UI；`compute_alerts` 对考核/履约版 `vid=None` 直接返回空（三版从未真正落地） |
| 核心模型 | 3 个 `plan_version` 行（内控/考核/履约），各自一份 `plan_node`；**`finish_inner` 作为各版本"计划完成日"规范字段**；考核/履约版 = 内控版 + 项目级"期量裕度"(buffer) 派生 |
| 三版差异来源 | 内控=紧计划；考核=内控+`buffer_kh` 天（留余量，考核不易误触延期）；履约=内控+`buffer_ly` 天（合同承诺基线）。裕度默认 0，可在项目表单配置 |
| 实际填报 | 新增独立页 `/project/<pid>/fill`，逐节点录 `actual_start/actual_finish/progress_pct`，保存后同步写三版并自动重算预警 |
| 闭环 | 生成内控 → 一键生成考核/履约 → 填报实际 → 预警对比计划 vs 实际 → 调整（仅改内控 base）→ 重新生成三版 |
| 改动面 | `01_ddl.sql`(project 加 2 列) + `engine.py`(`apply_to_project` 加 buffer) + `app.py`(生成/填报/对比 3 组路由 + 辅助函数) + 2 个新模板 + `project_detail.html` 导航 |

## 1. 现状盘点（改造前）

| 对象 | 现有状态 | 闭环缺口 |
|---|---|---|
| `plan_version` | 仅 `内控` 行（`app.py:144` 插入 `('内控','基准')`）；`考核/履约` 行从未创建 | 三版缺两版 |
| `apply_to_project` (`engine.py:287`) | 仅写 `finish_inner`，`finish_assess/finish_perform/actual_*` 全 `None` | 考核/履约版无数据、无实际值 |
| `edit_project_node` (`app.py:575`) | 仅编辑内控 base（project_node_rule/fixed），`recompute_project_finish` 只重算 `finish_inner` | 单节点调整不联动考核/履约版 |
| `compute_alerts` (`engine.py:306`) | 按 `plan_type` 取 `plan_version` 的 `vid`；考核读 `finish_assess`、履约读 `finish_perform`、均回退 `finish_inner` | 考核/履约版 `vid=None` → 直接 `return []`，预警永远只算内控 |
| `baseline_vid` (`app.py:500`) | 写死 `WHERE plan_type='内控'` | 无通用"取某版 vid"函数 |
| `project_detail` | 工具栏仅「重新计算预警（内控）」；节点表只显示 `finish_inner` | 无三版切换、无对比入口、无填报入口 |
| `finish_assess/finish_perform` 列 | DDL 已定义但全程未写（仅 `compute_alerts` 读） | 本方案**统一改用 `finish_inner` 作各版计划日**，这两列保留为预留/legacy（详见 §6 说明） |

**结论**：三版落地的实质工作量 = ① `project` 加 buffer 两列；② 新增"生成某版"函数（内控版已有，考核/履约版 = 内控 + buffer）；③ 新增实际填报页 + 对比页；④ `compute_alerts`/`baseline_vid` 通用化；⑤ 导航入口。

## 2. 设计模型：三版 = 内控 base + 版本裕度派生

```
                 ┌──────────── 内控版（紧计划，base）────────────┐
   T0 + offsets →│  plan_node.finish_inner = T0 + offset        │
                 └───────────────────────────────────────────────┘
                              │  + buffer_kh 天
                              ▼
                 ┌──────────── 考核版（留余量）──────────────┐
                 │  plan_node.finish_inner = T0 + offset + kh │
                 └─────────────────────────────────────────────┘
                              │  + buffer_ly 天
                              ▼
                 ┌──────────── 履约版（合同基线）────────────┐
                 │  plan_node.finish_inner = T0 + offset + ly │
                 └─────────────────────────────────────────────┘

   实际进度（同一事实）：actual_start/actual_finish/progress_pct
                 → 写入三版 plan_node（同步，保证各版预警一致）
```

- **内控版**：引擎按 T0 + 标准库规则推演的真实计划（现已有）。
- **考核版**：委托方考核用，通常比内控晚 `buffer_kh` 天（默认 0，可配），留有余量避免考核误判延期。
- **履约版**：合同履约承诺基线，比内控晚 `buffer_ly` 天（默认 0，可配）。
- **实际进度**：独立于版本，是真实世界事实，三版 plan_node 同步写入相同值。

> 为什么用 `finish_inner` 而非 `finish_assess/finish_perform`？每个 `plan_version` 已有独立 `plan_node` 行集，把"该版计划日"统一放 `finish_inner` 语义最干净、`compute_alerts` 也只需读 `finish_inner`。`finish_assess/finish_perform` 两列保留不删（避免破坏性 ALTER），本期不写入，文档标注为预留字段。

## 3. 数据模型改动

### 3.1 `project` 增加版本裕度两列（ALTER，双库通用）

```sql
ALTER TABLE project
  ADD COLUMN buffer_kh INT DEFAULT 0,   -- 考核版相对内控的期量裕度（天）
  ADD COLUMN buffer_ly INT DEFAULT 0;   -- 履约版相对内控的期量裕度（天）
```

> SQLite 与 MySQL 均支持多列 ADD（SQLite 单条 ALTER 多列也支持）。迁移脚本双库通用，经 `dbconn.get_conn()` 执行。

### 3.2 `plan_node` 不变（列已齐）

`finish_inner / actual_start / actual_finish / progress_pct / status` 均已存在，直接复用。

### 4.3 `app.py` · 新增 `generate_version(pid, plan_type, buffer_days)`

```python
def generate_version(pid, plan_type, buffer_days=0):
    """生成/重生成某版 plan_node（先删后插，整版覆盖）。基于当前生效引擎 + 项目 override。"""
    con = db(); cur = con.cursor()
    cur.execute("SELECT plan_start,prereq_json FROM project WHERE id=?", (pid,))
    pj = cur.fetchone(); con.close()
    eng = engine_for(pj["plan_start"], pj["prereq_json"], pid)
    vid = version_vid(pid, plan_type)
    con = db(); cur = con.cursor()
    if vid is None:
        cur.execute("INSERT INTO plan_version(project_id,version_no,plan_type,status) "
                    "VALUES(?,1,?,?)", (pid, plan_type, '基准'))
        vid = cur.lastrowid
    else:
        cur.execute("DELETE FROM plan_node WHERE project_id=? AND version_id=?", (pid, vid))
    con.commit()
    eng.apply_to_project(pid, vid, plan_type, buffer_days=buffer_days)
    con.close()
    return vid
```

### 4.4 `app.py` · 新增 `regenerate_all_versions(pid)`

```python
def regenerate_all_versions(pid):
    """内控/考核/履约三版统一重生成，保持与当前 base + buffer 一致。"""
    con = db(); cur = con.cursor()
    cur.execute("SELECT buffer_kh,buffer_ly FROM project WHERE id=?", (pid,))
    b = cur.fetchone(); con.close()
    generate_version(pid, "内控", 0)
    generate_version(pid, "考核", b["buffer_kh"] or 0)
    generate_version(pid, "履约", b["buffer_ly"] or 0)
```

> 调用时机：① 新建项目（`new_project` 在生成内控后追加生成考核/履约）；② `edit_project` T0/前置参数变更后；③ `edit_project_node` 单节点调整保存后（替换现有 `recompute_project_finish` 调用，使三版一致）。

def save_actual(pid, rows_actual):

## 10. 范围边界（不做）

- 审批流（用户已决策暂不启用）。
- 考核/履约版**单节点独立编辑**（本期考核/履约由内控 base + buffer 派生；如需逐节点微调留待 P2）。
- 差异存储 / 版本快照（属标准库版本化方案范畴，不在本方案）。
- `finish_assess/finish_perform` 两列启用（本期统一用 `finish_inner`，保留列占位）。
- 移动端 / 投资测算（需求规格 P1，不在本方案）。
